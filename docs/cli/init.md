# `eg init` — one-command repository bootstrap (issue #229)

`eg init` bootstraps a repository into a fully queryable embedded
`AletheiaDB` store with a single command:

```powershell
eg init . --data-dir .egregore
```

It orchestrates the existing capture pipeline in-process — the same
functions the individual commands use, so the store it builds cannot drift
from the documented multi-step sequence:

1. **`scan_tree`** — `eg scan` over the current working tree
2. **`ingest_tree`** — `eg ingest … --adapter embedded --data-dir <dir> --embed`
   over the tree graph (semantic embeddings generated by default)
3. **`scan_history`** — `eg scan-history` Git history replay (read-only;
   the working tree and Git state are never mutated)
4. **`ingest_history`** — the second `eg ingest` over the history graph
   (structural, no `--embed` — exactly like the manual sequence)

Intermediate graph JSONL lives in a system temporary directory, never in
the repository being bootstrapped. `init` is fully offline except for the
one-time embedding-model download (cached afterward by the embeddings
feature's model cache).

## Semantics: on by default, never silent

Embedding generation is **on by default** — `eg init` is the onboarding
path and the store it produces should answer `query semantic` out of the
box. There are exactly three ways to get a structure-only store, and every
one is loudly reported in the bootstrap report's
`semantics.skipped_reason` field:

- the operator passed `--no-embed`;
- the binary was built without the `embeddings` feature;
- generation failed (for example the model is unavailable). The bootstrap
  **continues structurally** — this is the issue #229 partial-failure
  contract, not a fatal error — and the reason is recorded.

The store records the embedding-model identity in its vector-index identity
(issue #104): if an existing store's index was built by a **different**
model, the bootstrap refuses before writing anything (exit 2; see below)
rather than blending two vector spaces. Use a fresh `--data-dir` to
re-bootstrap with another model.

Only the current-tree batch is embedded — the history batch ingests
structurally, exactly like the manual sequence below whose second
`eg ingest` passes no `--embed`. Temporal history records therefore carry
no vectors; `query semantic` ranks the current tree.

`--embed-model` selects the model with the same precedence as
`eg ingest --embed`: `--embed-model` > `[embeddings].model` in
`egregore.toml` > built-in default
(`sentence-transformers/all-MiniLM-L6-v2`, 384 dimensions).

## History safety

The history stage reads Git objects read-only — the same lane contract as
`eg scan-history`. `eg init` never writes to the working tree, never
touches `HEAD`, and never mutates Git state. Integration coverage pins
this: a bootstrapped repo's `git status`, tracked-file bytes, and `HEAD`
are byte-identical before and after `init`.

In a repository that is not a Git checkout (or has no history), the
history stage is **skipped** with a recorded reason — the bootstrap
reports `store_state: "partial_history"` and the tree store stays fully
queryable. History-stage failures are likewise recorded as stage
`failed`/`skipped` and reported; the store from the completed stages is
still usable.

## Idempotency: `exit 3` means "already current"

A second `eg init` on an unchanged repository converges to a no-op instead
of rebuilding. `init` asks the same freshness question as
`eg freshness --data-dir` — the store's recorded source snapshot (same
snapshot rules, including `--repo-id-override` semantics) — and additionally
requires two things:

1. the requested semantic state is present (a vector-index identity for the
   resolved model when embeddings are requested; a structural store is
   already current under `--no-embed`);
2. **history completeness** — when the repository has a commit tip, the
   store holds a live `Commit` node for the current HEAD. A previous run
   whose history stages were skipped or failed leaves the tree indexed but
   temporal history absent; converging to a no-op there would report
   `already_current` over a store that can never grow its history, so the
   probe rebuilds instead and history gets another chance. The tip lookup is
   read-only (`git rev-parse HEAD` never touches the working tree or Git
   state).

When all three hold, nothing is rebuilt and `init` exits with code **3**
(`status: "already_current"`). A no-op over a repository with no commit tip
(non-Git directory, unborn HEAD) honestly reports
`store_state: "partial_history"` — history replay had nothing to index.

## Exit codes

| Code | Meaning |
| ---- | ------- |
| `0`  | The store was built or rebuilt and is queryable. `status` is `rebuilt` when every attempted stage completed and embeddings reached their requested state; `partial` when an optional stage was skipped or failed, or embeddings were requested but unavailable — the report names every stage either way. |
| `1`  | A required stage failed (the tree scan or a graph ingest). The bootstrap report is printed **first** so it names the completed and failed stages; the store is left exactly as the manual sequence would leave it. |
| `2`  | Refused before writing anything: the ingest capacity preflight (issue #439) fired, or the embedding-index identity conflict fired. The store is untouched; use a fresh `--data-dir` to re-bootstrap. |
| `3`  | Already current: no rebuild was needed (`status: "already_current"`). |

## The bootstrap report

`--format json` (the default) prints a machine-readable report on stdout;
`--format text` renders the same fields as stable human-readable lines.
Required-stage failures and refusals print their reports before exiting,
so callers always get the stage breakdown.

Fields:

- `status` — `rebuilt` | `already_current` | `partial` | `failed`
- `repository` — `id`, `identity_source`, `path`
- `data_dir` — the data directory bootstrapped into
- `stages` — one entry per stage: `name`, `status`
  (`completed` | `skipped` | `failed`), `records` produced or attempted,
  `succeeded` (ingest stages), and `detail` (skip reason or failure message)
- `records` — `total` plus `per_domain` counts read back from the store
- `semantics` — `present` (vector-index identity recorded), `model`
  (bounded identity: provider, name, version, dim, content_hash), and
  `skipped_reason` when embeddings were skipped
- `snapshot` — the indexed source snapshot: `head` (the bare commit SHA, or
  `no_git` / `unborn_head` when there is no commit to name, `unknown` when
  the store carries no snapshot) and `dirty`
- `store_state` — `complete` | `structural_only` (semantics requested but
  skipped) | `partial_history` (history absent or incomplete)

## Manual equivalent

`eg init . --data-dir .egregore` is equivalent to:

```powershell
eg scan . --out tree.jsonl
eg ingest tree.jsonl --adapter embedded --data-dir .egregore --embed
eg scan-history . --out history.jsonl
eg ingest history.jsonl --adapter embedded --data-dir .egregore
```

The multi-step sequence remains the documented manual path when you need
finer control — inspecting an intermediate graph, skipping history, or
passing flags `init` does not expose. The two produce a behaviorally
equivalent queryable state — integration tests assert equivalence
(`query symbol`, `query context`, `query semantic`) between them.

One deliberate divergence: before ingesting the history batch, `init`
rewrites the history graph's `Repository` snapshot to the tree scan's
snapshot. The history replay stamps `dirty=false` (committed HEAD state)
so a standalone history graph reads as freshness-clean, but merged into
the tree's store that stamp would supersede the tree's and misreport a
dirty working tree as clean — and reverting the edits afterwards would
then converge to a false `already_current`. The manual sequence keeps the
history replay's stamp; `init` keeps the tree's, so the store's snapshot
always describes the tree that was actually scanned.

## Partial-store guarantees

- A stage that **fails required** leaves behind exactly what the manual
  sequence would leave behind at the same point — no half-written
  indexes, no corrupt store. The report names the completed stages and
  the failure.
- A stage that is **skipped or fails optionally** (embeddings, history)
  still leaves a valid, non-corrupt store for everything that completed:
  structural queries keep working when semantics are skipped, and the
  tree graph keeps working when history is skipped. The report's
  `store_state` and per-stage `detail` say precisely what is missing.
- A **refusal before writing** leaves the store untouched (exit 2).
